# DermPal Database Design

## 1. Entities

I chose six entities for the DermPal database:

| Entity | Information stored |
|---|---|
| user | A registered DermPal user |
| assessment | One skin-image submission and its analysis record |
| assessment_image | Metadata and storage reference for each uploaded skin image |
| model_version | Information about the AI models and their versions |
| prediction | An AI-generated skin-type classification or acne prediction |
| recommendation | Skincare recommendations associated with a prediction |

I keep assessment and assessment_image separate because one assessment can contain multiple uploaded images. For example, a user may upload three skin photographs in one submission, but they belong to the same assessment.

## 2. Attributes and keys

Each entity has an automatically generated ID. `BIGINT` stores whole numbers, `VARCHAR` stores text, `TEXT` stores longer text, `TIMESTAMPTZ` stores date and time, `NUMERIC` stores decimal values, and `BOOLEAN` stores true or false.

| Entity | Attributes and proposed PostgreSQL types | Keys and required values |
|---|---|---|
| user | user_id BIGINT; full_name VARCHAR(120); email VARCHAR(254); role VARCHAR(30); created_at TIMESTAMPTZ | PK: user_id. Unique: email. All required. Role is restricted to user, administrator or reviewer. |
| assessment | assessment_id BIGINT; user_id BIGINT; submitted_at TIMESTAMPTZ; status VARCHAR(20) | PK: assessment_id. FK: user_id → user.user_id. All required. Status is restricted to pending, processing, completed or failed. |
| assessment_image | image_id BIGINT; assessment_id BIGINT; file_name VARCHAR(255); storage_reference TEXT; content_type VARCHAR(100); uploaded_at TIMESTAMPTZ | PK: image_id. FK: assessment_id → assessment.assessment_id. All required. Storage reference is unique. |
| model_version | model_version_id BIGINT; model_name VARCHAR(100); model_type VARCHAR(20); version VARCHAR(30); created_at TIMESTAMPTZ | PK: model_version_id. Unique: model_name and version together. All required. Model type is restricted to skin_type or acne. |
| prediction | prediction_id BIGINT; assessment_id BIGINT; model_version_id BIGINT; prediction_type VARCHAR(20); predicted_class VARCHAR(50); predicted_at TIMESTAMPTZ | PK: prediction_id. FKs: assessment_id → assessment.assessment_id; model_version_id → model_version.model_version_id. All required. |
| recommendation | recommendation_id BIGINT; prediction_id BIGINT; recommendation_text TEXT; created_at TIMESTAMPTZ | PK: recommendation_id. FK: prediction_id → prediction.prediction_id. All required. |

The actual image files are stored outside PostgreSQL, for example in cloud object storage. The `storage_reference` field records where each image is located.

## 3. Relationships

| Tables linked | Relationship | Meaning |
|---|---|---|
| user → assessment | One to many | A user can have zero or more assessments. Each assessment belongs to exactly one user. |
| assessment → assessment_image | One to many | An assessment contains one or more images. Each image belongs to exactly one assessment. |
| assessment → prediction | One to many | An assessment can have zero or more predictions. Each prediction belongs to exactly one assessment. |
| model_version → prediction | One to many | A model version can generate zero or more predictions. Each prediction references exactly one model version. |
| prediction → recommendation | One to many | A prediction can have zero or more recommendations. Each recommendation belongs to exactly one prediction. |

For example, one assessment can have a skin-type prediction and an acne prediction, each generated by its corresponding AI model.

## 4. Business rules and constraints

1. **Unique users:** A primary key identifies each user, while a unique constraint prevents duplicate email addresses.
2. **Assessment ownership:** A foreign key ensures every assessment belongs to an existing user. The user can have multiple assessments.
3. **Image submissions:** A foreign key ensures every image belongs to an existing assessment. Each assessment must contain at least one image. This minimum-image requirement needs transaction or application-level validation because a foreign key alone cannot enforce it.
4. **Prediction references:** Primary and foreign keys ensure each prediction has a unique ID and references an existing assessment and model version.
5. **Prediction types and classes:** CHECK constraints restrict prediction types to `skin_type` or `acne`. Additional validation ensures predicted classes correspond to the selected prediction type. The model type must also match the prediction type.
6. **Confidence and timestamp:** A CHECK constraint restricts confidence scores to values between 0 and 1, inclusive. `predicted_at` must be provided.
7. **No duplicate predictions:** A composite unique constraint on `assessment_id`, `model_version_id` and `prediction_type` prevents duplicate predictions of the same type from the same model version within an assessment.
8. **Recommendations:** A foreign key ensures every recommendation references an existing prediction. Application or transaction logic ensures recommendations are generated only after the relevant prediction is completed.

## 5. Design assumptions

1. Users can submit multiple skin images in one assessment, and each assessment can contain both skin-type and acne predictions.
2. DermPal uses separate AI models for skin-type classification and acne analysis, with each model identified by its version.
3. Image files are stored in external object storage, while PostgreSQL stores their metadata and storage references.
